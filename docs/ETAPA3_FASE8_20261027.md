## Lista exacta de siete productores

| Tipo NOT-01 | Operación real y condición | Destinatario / recurso / deduplicación |
|---|---|---|
| FILE_SHARED | ShareService.shareFile → compartir INSERT activo o reactivación real; recurso no expirado | Receptor NEW; archivo NEW.id_archivo. Clave share:id:txid de la transición. |
| FOLDER_SHARED | ShareService.shareFolder → compartir INSERT activo o reactivación real; recurso no expirado | Receptor NEW; carpeta NEW.id_carpeta. Misma política de transición, tipo separado. |
| ACCESS_REVOKED | ShareService.revokeShare → compartir estado 1→2 | Receptor y recurso OLD que pierden el acceso. Clave revoke:id:txid. Repetir el estado no notifica. |
| PAYMENT_APPROVED | RPC de contratación/renovación/cambio o escritor autorizado → pago Aprobado nuevo o transición a Aprobado, monto positivo | pago.id_usuario, o usuario de su suscripción si falta. Recurso pago/id. Clave payment:id. No rechazo ni Q0/asiento de crédito. |
| SUBSCRIPTION_ACTIVATED | RPC de alta/renovación/upgrade, activación diferida del worker o inserción Free → suscripción vigente nueva o transición desde estado no vigente | Suscripción.id_usuario; recurso suscripcion/id. Clave subscription:id. Pendiente/futura/vencida no activa aviso. Activa→PorVencer no duplica activación. |
| SUBSCRIPTION_EXPIRING | Worker existente cambia a PorVencer, o escritor autorizado confirma esa transición/fecha, para un plan pagado vigente | Usuario de la suscripción; recurso suscripcion/id. Clave expiring:id:fecha_fin. No un aviso cada hora. |
| STORAGE_NEAR_LIMIT | QuotaService.syncUsedStorage/updateUsedStorage confirma usuario.espacio_usado_by >=90% de cuota vigente; Free real si no hay suscripción | Usuario afectado; recurso almacenamiento/usuario.id. Una clave por asignación de cuota (subscription:id o Free:id), no por consulta ni archivo. |

Los primeros tres comparten `cloudbox_not_share`; pago usa `cloudbox_not_payment`; los dos de suscripción usan `cloudbox_not_subscription`; uso usa `cloudbox_not_storage`. Son siete productores lógicos en cuatro triggers. La identidad transaccional permite revocar y volver a compartir el mismo registro incluso dentro del mismo día, sin añadir una versión artificial al recurso. En una misma transacción se deduplica cada tipo/recurso compartido; no se emiten mensajes por cada UPDATE sin cambio.

El umbral 90% y una advertencia por asignación de cuota son decisiones explícitas para el evento near-limit, cuyo contrato no fijaba porcentaje. No se rearma al liberar unos bytes ni al borrar el aviso; una nueva suscripción/asignación permite otro aviso. Se observa uso real persistido, incluso durante una consulta que sincroniza cuota: una carga rechazada no incrementa el uso ni produce un aviso de carga exitosa, pero una observación confirmada de un uso ya cercano al límite puede generar su advertencia válida.

## Actividad, auditoría y seguridad

- GET /api/activity conserva success/data y el usuario de req.user.id; from/to son fechas UTC con límite final exclusivo del día siguiente, action se filtra mediante igualdad e inner join solo al filtrar, limit/offset validados y orden fecha DESC/id DESC. Sin filtro se conservan acciones huérfanas del join. Se valida también la identidad interna; no se admiten IDs enteros fuera de int4.
- LogAuditoria sigue separado de actividad. Se conservaron los registros existentes de usuarios/roles y middleware de archivos/carpetas; se añadieron llamadas AUD-01 después del éxito de creación/cambio/estado de planes, cancelación (incluida programación) y revocación. No se registran esos casos también en middleware. Un registro por petición confirmada; los reintentos HTTP exitosos pueden auditar el intento nuevamente, sin duplicación por dos enganches.
- Los detalles de auditoría nuevos son listas permitidas de operación/estado programado/fecha efectiva; no se almacena el cuerpo HTTP ni secretos. recordLog mantiene su comportamiento best effort. Las rutas administrativas y de usuario siguen reutilizando los middlewares existentes.
- GET /api/notifications y /unread mantienen paginación y orden fecha_creacion DESC/id DESC. Toda consulta/escritura/borrado filtra por receptor. PATCH /:id/read conserva la fila y añade read:true, usando leida=true como estado. PATCH /read-all devuelve el conteo exacto. DELETE devuelve 204 y un ID ausente/ajeno sigue dando 404.
- leida=true con fecha_lectura=NULL es un histórico válido. Repetir lectura no inventa hora ni la modifica. Se admiten títulos nuevos de hasta 255 caracteres por compatibilidad con el esquema real, sin truncar lecturas históricas. Tipos antiguos/nulos y mensajes existentes se leen sin imponer los siete tipos a los datos anteriores.
- El registro mínimo cloudbox_notification_event conserva idempotencia después de borrar avisos. No es cola, no contiene cuerpos y no tiene rutas públicas. Creación solo mediante NOT-01 interno/RPC autorizada. Errores HTTP no exponen detalles internos.

## Dependencias externas, límites y comprobación manual

La integración de productores está implementada localmente; **ninguno se declara ya activo/verificado en Supabase** hasta instalar el SQL y comprobar el flujo real. SUBSCRIPTION_EXPIRING depende de la ejecución normal del worker/cron existente y de la transición a PorVencer. SUBSCRIPTION_ACTIVATED diferida depende también del worker. STORAGE_NEAR_LIMIT depende de la sincronización persistida de uso; escrituras realizadas fuera del backend no se observan hasta que se sincronice. PAYMENT_APPROVED observa registros aprobados, no introduce una pasarela externa. No hay email/push/WebSocket ni entrega garantizada.

Los triggers AFTER participan en la transacción principal: las notificaciones son visibles únicamente al commit. Una excepción ordinaria del productor revierte su subtransacción (incluido claim) y emite advertencia genérica, sin revertir la operación principal. Un fallo del sistema completo o una cancelación de la transacción no implica entrega. No se incluye reintento automático ni backfill de avisos anteriores a la instalación.

Antes de una aplicación futura autorizada: revisar/guardar inspección, comprobar que no hay deriva, disponer de la versión de backend compatible y coordinar los scripts/activación que se aprueben. Mantener la espera acordada del SQL comercial; etapa 3 no lo ejecuta ni sustituye. No ejecutar el histórico 20261025040000 ni recrear notificacion. El cron no se cambia ni se lanza globalmente como prueba. Ver el README de SQL para pasos y contingencia.

Pruebas reales pendientes, realizadas por el usuario con cuentas propias A/B y administrador:
